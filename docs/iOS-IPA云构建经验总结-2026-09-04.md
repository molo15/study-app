## 三、真正的根因分析

### 3.1 最初的误判

前 14 次失败都被归因于"代码签名 / Development Team"问题，但实际上：

- **Xcode build 本身是成功的**（日志显示 `Xcode build done. 55.4s`）
- **Flutter 在最后一步做了 Development Team 检查**，发现没有就报错退出
- 但报错退出时，**Dart 编译阶段可能已经失败了**，只是被代码签名错误掩盖了

### 3.2 真正的根因：Dart 编译错误

```
lib/ui/practice_summary.dart:25:15: Error: The method 'GlassAppBar' isn't defined
```

- V3 UI 重设计时，`GlassAppBar` 组件被移除/重构
- `practice_summary.dart` 是 `practice_page.dart` 的 **part 文件**（`part of 'practice_page.dart';`）
- `practice_page.dart` 没有导入 `glass_app_bar.dart`，导致编译时找不到 `GlassAppBar`
- Dart 编译失败 → `kernel_snapshot_program` 失败 → Xcode build 失败
- 但错误信息被 Flutter 的 Development Team 检查错误**掩盖**了，导致前 14 次都在错误的方向上修复

### 3.3 为什么 09-03 能成功？

- 09-03 的代码（commit `e028fe5`）还没有 V3 UI 重设计
- `practice_summary.dart` 中可能还没有引用 `GlassAppBar`，或者 `GlassAppBar` 还存在
- 最简配置 `flutter build ios --release --no-codesign` 直接成功

## 四、最终成功的配置

### 4.1 Workflow 关键步骤

```yaml
- name: Inject dummy Development Team and disable signing
  working-directory: app/ios
  run: |
    sed -i '' 's/CODE_SIGN_STYLE = Automatic;/CODE_SIGN_STYLE = Manual;/g' Runner.xcodeproj/project.pbxproj
    perl -i -pe 's/PRODUCT_BUNDLE_IDENTIFIER = dev\.kaoyan\.quizApp;/PRODUCT_BUNDLE_IDENTIFIER = dev.kaoyan.quizApp;\n\t\t\tDEVELOPMENT_TEAM = 0000000000;/g' Runner.xcodeproj/project.pbxproj

- name: Build iOS (release, no codesign)
  working-directory: app
  env:
    CODE_SIGNING_REQUIRED: "NO"
    CODE_SIGNING_ALLOWED: "NO"
    CODE_SIGN_IDENTITY: ""
  run: |
    rm -f ios/Podfile ios/Podfile.lock
    flutter build ios --release --no-codesign
```

### 4.2 关键配置说明

| 配置项 | 值 | 作用 |
|--------|-----|------|
| `CODE_SIGN_STYLE` | `Manual` | 关闭自动签名，避免 Xcode 自动查找证书 |
| `DEVELOPMENT_TEAM` | `0000000000`（假值） | 让 Flutter 的预检通过，不做真实签名 |
| `CODE_SIGNING_REQUIRED` | `NO` | Xcode 不要求签名 |
| `CODE_SIGNING_ALLOWED` | `NO` | Xcode 不允许签名 |
| `CODE_SIGN_IDENTITY` | `""` | 清空签名身份 |
| `--no-codesign` | Flutter 标志 | Flutter 层面禁用签名 |

## 五、关键经验教训

### 5.1 错误排查优先级

1. **先看完整的构建日志**，不要只看最后一行错误
2. **Dart 编译错误会被 Flutter 的代码签名检查掩盖**——如果看到 `Xcode build done` 后立即报 Development Team 错误，要往上翻找是否有 Dart 编译错误
3. **`flutter analyze` 是最快的验证方式**——本地跑一次就能发现所有编译错误，不需要等云端构建

### 5.2 YAML 语法陷阱

- **sed 的 `a\` 命令**（追加文本）在 YAML 的 `run: |` 块中会导致解析错误，因为 `a\` 后面需要跟换行符
- **python3 多行字符串**中的 `\n\t` 在 YAML 中也会导致解析问题
- **推荐用 perl 单行命令**做文件修改，避免多行字符串

### 5.3 未签名构建的正确姿势

- 光靠 `--no-codesign` 不够，Flutter 仍会检查 DEVELOPMENT_TEAM
- 需要注入假的 DEVELOPMENT_TEAM 让预检通过
- 同时用环境变量三重禁用真实签名
- `rm -f ios/Podfile ios/Podfile.lock` 让 Flutter 重新生成 CocoaPods 配置

### 5.4 part 文件的 import 陷阱

- `part of 'xxx.dart';` 文件共享主文件的 import
- 如果主文件没有导入某个组件，part 文件中引用就会编译错误
- V3 重构时要特别注意 part 文件中的组件引用是否仍然有效

## 六、常见问题排查指南

### Q1：构建报 "Building a deployable iOS app requires a selected Development Team"

**排查步骤**：
1. 往上翻日志，看是否有 Dart 编译错误（`Error: The method 'xxx' isn't defined`）
2. 本地跑 `flutter analyze` 确认没有编译错误
3. 确认 workflow 中注入了假的 DEVELOPMENT_TEAM
4. 确认环境变量 `CODE_SIGNING_REQUIRED=NO` 等已设置

### Q2：构建报 YAML 语法错误

**排查步骤**：
1. 检查是否用了 sed `a\` 命令（会导致换行符问题）
2. 检查是否用了 python3 多行字符串（`\n\t` 会导致问题）
3. 推荐改用 perl 单行命令
4. 本地用 `yamllint` 或在线 YAML 校验工具验证

### Q3：构建报 `build/ios/iphoneos/: No such file or directory`

**原因**：Flutter 构建在 Xcode 之前就失败了，Runner.app 没有生成
**排查步骤**：
1. 往上翻日志，找 Dart 编译错误
2. 本地跑 `flutter analyze`
3. 确认 `flutter build ios --release --no-codesign` 能在本地成功（如果有 macOS 环境）

### Q4：构建成功但 IPA 安装后闪退

**排查步骤**：
1. 确认 IPA 是 arm64 架构（`lipo -info Runner.app/Runner`）
2. 确认自签时用了正确的证书和描述文件
3. 查看设备日志（Xcode → Window → Devices and Simulators）
4. 确认 Info.plist 中的权限配置正确

## 九、总结

今天的 18 次构建失败，核心教训是：

1. **不要被表面错误误导**——Flutter 的 Development Team 错误可能掩盖了真正的 Dart 编译错误
2. **本地验证优先**——`flutter analyze` 1 分钟就能发现的问题，不要等云端构建 3 分钟才发现
3. **YAML 语法要谨慎**——避免 sed `a\` 和 python3 多行字符串，优先用 perl 单行命令
4. **part 文件的 import 是隐性依赖**——重构时要特别注意

最终成功的配置已经验证可用，后续构建只需保持当前 workflow 不变，提交前跑 `flutter analyze` 即可。
