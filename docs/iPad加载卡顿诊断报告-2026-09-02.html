iPad 访问 GitHub Pages 长时间加载诊断报告

站点 https://molo15.github.io/study-app/ · Flutter Web（CanvasKit + dart2js + PWA）· 诊断日期 2026-09-02 · 构建 BUILD_ID 666caf7d7bbb / v1.4.0+15
结论：不是单一问题，而是三层叠加，且三层都在 iPad 上被放大。
  1. 网络层（决定性）：GitHub Pages 的 Fastly 节点 IP（185.199.108–111.153）在当前国内运营商下 TCP 握手连续超时（本机实测 5/5 次失败，同期百度 0.2s、fonts.gstatic.com 0.31s 正常）——线路本身不通或极慢，再小的包也传不过来。
  2. 构建配置层（iPad 独有浪费）：iPad 上所有浏览器都是 WebKit 内核，Flutter 会选用 full 版 canvaskit.wasm（7.28MB）；但 index.html 的 preload 和 sw.js 预缓存写死的是 chromium 版（5.43MB）——iPad 白白下载 5.26MB 用不上的文件，真正的引擎还要再下一遍。iPad 冷启动首屏原始字节 19.46MB，比桌面 Chrome 的 12.43MB 多 56%。
  3. 设备性能层（白屏时间被拉长）：项目自测基线里，桌面 CPU 仅 WASM 编译 + main.dart.js 执行就要约 3.3s；iPad（尤其 A12 级别的 mini 5）单核性能远弱于桌面，且 iOS 不支持 WasmGC、只能跑 3.47MB 的 dart2js 包，编译执行阶段预计 10 秒级。期间页面是纯白屏，没有任何加载提示。

1.3 变体错配的代码证据

  • flutter_bootstrap.js 的引擎选择逻辑：仅当浏览器同时具备 hasChromiumBreakIterators 与 hasImageCodecs（判定为 Chromium 内核）时才用 chromium 子目录变体；WebKit（苹果全系浏览器）两个能力检测均为 false → 回退加载根目录 full 变体 canvaskit.wasm（7.28MB）。
  • web/index.html 第 42–43 行写死 preload canvaskit/chromium/canvaskit.js + .wasm，在 iPad 上 100% 不会被引擎使用，但浏览器仍会照单下载。
  • sw.js 的 SHELL_ASSETS 同样写死 ./canvaskit/chromium/canvaskit.wasm：SW 安装时把 5.43MB 无用文件再拉一遍，而 iPad 真正需要的 full 变体反而不在预缓存清单里。
  • 部署包内 index.html 的 base href 已正确写成 /study-app/，路径配置没有问题，可排除"子路径 404"假设（注意：本地 build/web 目录当前那份是 base href="/" 的旧构建，不能直接重新部署，否则反而会 404）。

2. iPad 冷启动完整链路与阻塞点

① TCP 建连到 185.199.x.153:443，国内运营商下握手丢包/超时，可能卡数十秒到数分钟，每一个资源都要复用这条劣化链路。
② index.html + bootstrap约 16KB，下载后解析出 4 个 preload。
③ 4 个 preload 并行main.dart.js 3.47MB、中文字体 2.97MB、chromium wasm 5.43MB（iPad 用不上）、chromium js。
④ main.dart.js 执行引擎初始化，发现 WebKit 不支持 chromium 变体，重新发起 full canvaskit.js + canvaskit.wasm 7.28MB 下载。
⑤ 数据库并行sqlite3.wasm 0.73MB + sqflite_sw.js 0.26MB。
⑥ CPU 编译执行7.28MB wasm 编译 + 3.47MB JS 解析执行，桌面级 CPU 自测约 3.3s，A12 级 iPad 预计 10 秒级，期间纯白屏。
⑦ window load 后才注册 SW若前面任一资源没下完，load 事件不触发 → SW 永远装不上 → 下次打开仍是全量冷启动，缓存机制形同虚设。

恶性循环：弱网下首访很难完整跑完 → SW 不注册 → 永远没有"第二次秒开"；而 SW 安装时还会把 shell 清单（含 5.43MB 无用 chromium wasm、3.47MB 主程序、2.97MB 字体）再 fetch 一遍，与页面请求争抢本就拥塞的链路。

3. 次要问题（同样会在 iPad 上拖慢/添堵）

问题证据影响
白屏无任何加载指示index.html 的 body 只有一个 script 标签，无 loading 动画/进度用户无法区分"在加载"还是"卡死"，主观上就是"加载不出来"
残留 Google 字体回退地址main.dart.js 内仍有 1 处 https://fonts.gstatic.com/s/（引擎字体回退默认值）子集字体未覆盖的生僻字/emoji 会触发境外分片拉取，弱网下挂起，可能卡住文字渲染
.gz 预压缩未随包部署部署 zip 47 个文件无 .gz；构建目录里的 .gz 是给 nginx gzip_static 的GitHub Pages 虽会动态 gzip，但 wasm 等类型压缩不保证；带上同名 .gz 可让 Pages 直接发静态压缩版（社区已验证会自动带 Content-Encoding: gzip）
iOS Safari 的缓存淘汰策略ITP 对 Service Worker/Cache Storage 有 7 天不访问即清除的机制即使首装成功，隔一周不用又要全量重来
大文件无断点续传保障main.dart.js 单文件 3.47MB、wasm 5–7MB，Safari 传输中断需整体重下劣化链路上大文件失败概率随体积线性上升

4. 修复方案（按杠杆排序）

P0把站点搬到国内能稳定到达的托管 —— 解决"线路不通"这个决定性问题

  • 首选：腾讯云 COS / 阿里云 OSS 静态网站托管 + CDN（学生机/低成本即可，9MB 压缩流量走国内边缘节点通常 1–3 秒）；同一套 build/web 原样上传。
  • 自有国内云服务器亦可（nginx 开 gzip_static / brotli_static，正好用上构建产物里的 .gz）。
  • 零成本备选可试 Cloudflare Pages / Vercel，但二者在国内可达性同样不保证，只能当试验，不能当解决方案；Gitee Pages 类服务以其当前实际开放状态为准。
  • 无论搬到哪，下面 P0/P1 的构建侧修正都应该一起做。

P0消除 iPad 的 5.26MB 白下载：按内核选择 preload / 预缓存变体

  • index.html 中删掉写死的 chromium preload，改为一小段内联脚本：navigator.vendor === 'Apple Computer, Inc.'（WebKit）时 preload 根目录 full 变体，Chromium 时才 preload chromium/ 目录；拿不准时宁可不 preload wasm（让引擎自己选，最多损失并行度，不会下错）。
  • sw.js 的 SHELL_ASSETS 同步修正：WebKit 场景缓存 ./canvaskit/canvaskit.wasm；或构建时按 UA 输出两份清单。至少应把 full 变体补进清单。
  • 预期收益：iPad 冷启动原始字节 19.46→14.20MB，gzip 口径 9.08→7.09MB，且 SW 不再重复拉错文件。

P1让缓存机制真正生效 + 给用户可见反馈

  • SW 注册从 window.load 提前到 bootstrap 解析后立即注册（或至少不依赖全部资源 load 完成），避免弱网首访永远装不上 SW。
  • SW install 的 shell 预缓存改为分批/后台进行，不与首屏请求争抢连接；对已在 HTTP 缓存中的资源自然复用。
  • index.html 内加轻量首屏 loading（纯 CSS 动画 + "正在加载学习引擎…"文案，资源就绪后由 Flutter 接管移除），消除白屏焦虑。
  • 部署时把 .gz 一并上传到 GitHub Pages（若继续保留该镜像），并在线用 curl -I -H "Accept-Encoding: gzip" 确认 wasm/js 响应带 Content-Encoding: gzip。

P2继续做减法（边际收益，建议托管问题解决后再评估）

  • main.dart.js 用 deferred imports 拆首屏不用的模块（模拟卷、统计等），gzip 后 1.02MB 有机会减半。
  • 中文字体子集按实际题库用字再裁剪（当前 2.97MB 是第二大单项）；并显式配置 CanvasKit 字体回退，避免运行时触碰 fonts.gstatic.com。
  • 长期跟踪 dart2wasm：iOS 需 Safari 18.2+ 才支持 WasmGC，Flutter 对 Safari 的 wasm 构建尚未默认启用；旧 iPad 升级到支持的系统版本后才可评估，届时可出 dart2js + dart2wasm 双构建自动回退。

5. 修复后如何在 iPad 上验证

  1. 无 Mac：在 index.html 临时注入一段 performance 计时浮层（navigationStart 到首帧、各资源 transferSize），或直接用 Safari 地址栏旁的"刷新-对比"观察：正确配置下 iPad 网络面板里不应再出现 chromium/canvaskit.wasm 这条请求。
  2. 有 Mac：iPad 设置 → Safari → 高级 → Web 检查器，连线后用 Mac Safari 开发菜单看 Network 瀑布与 Console，确认：①只请求一个 canvaskit.wasm（full）；②SW 成功注册且二次打开 transferSize=0；③无 fonts.gstatic.com 请求。
  3. 对比口径沿用项目《性能基线报告》方法：清缓存/SW 为冷加载，SW 命中为热加载，分别记录 FCP 与总传输。
