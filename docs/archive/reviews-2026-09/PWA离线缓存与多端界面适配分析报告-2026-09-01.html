1PWA 离线缓存分析

1.1 现状诊断

缺口当前 Web 离线不可用。flutter_service_worker.js 是 Flutter 新版生成的「注销空壳」（31 行，仅 unregister() 自己、无任何资源缓存逻辑）；index.html / flutter_bootstrap.js 均无 Service Worker 注册。违背方案 §3.1「PWA：manifest + 加主屏，离线缓存，图标」。
检查点当前状态说明
manifest（可加主屏）✅ 已具备中文名「考研刷题」、standalone、主题色 #0F1214、192/512 图标
离线缓存（SW 缓存资源）✗ 缺失SW 为注销空壳，无 Cache API 逻辑
SW 注册入口✗ 缺失bootstrap / index 均未注册

1.2 为什么这是真问题

  • 设备矩阵决定的：iPad mini 5 无法构建 iOS 原生包，方案明确走 Web / PWA 加主屏——这正是离线缓存的核心场景（通勤、地铁、无网自习）。
  • 体积大、弱网敏感：冷启动需下载 canvaskit 5.4MB + main.dart.js 3.4MB + 中文字体 3MB ≈ 11.8MB 静态资源；无缓存时每次联网都重新拉取。
  • 可安装性：部分浏览器（如 Chrome）对 PWA 安装条件要求含 SW；缺 SW 影响「添加到主屏幕」的完整体验。
  • 数据在本地：App 数据全在 IndexedDB / localStorage，完全具备离线运行的条件，只是资源层没有缓存。

1.3 行业方案：PWA 离线缓存策略

核心是 Service Worker + Cache API 协同（SW 拦截网络请求、按策略读写缓存）。不同资源适用不同策略：

策略适用资源行为本项目对应
Cache First（缓存优先）不常变的静态资源命中缓存即返回，未命中才请求并写入字体、canvaskit wasm、main.dart.js、图标
Network First（网络优先）入口 HTML / 变化数据先请求网络，失败回退缓存index.html 首屏
Stale-While-Revalidate需兼顾速度与新鲜度先返回缓存，后台拉新更新题库包（版本化资源）
仅网络 / 仅缓存支付、实时接口 / 固定资源极端策略本项目 API 类暂不适用

来源：CSDN《Service Worker 做离线缓存，PWA 实战》、阿里云《PWA 离线优先策略》、Vibe Studio《Efficient Caching Strategies For Flutter Web Apps》。

1.4 针对本项目的推荐实施路径

  1. 自定义 service worker（推荐，避免引入 Workbox 构建链）：手写 sw.js，install 阶段 precache 应用壳（main.dart.js、canvaskit 实际用到的 chromium 变体、woff2 字体、manifest、favicon、题库 zip 可选）；fetch 阶段按 1.3 策略分发。
  2. 注册入口：在 web/flutter_bootstrap.js（已自定义）的 load 后注册 sw.js，不阻塞首帧。
  3. 版本控制：复用 Flutter build 生成的 serviceWorkerVersion 哈希做缓存命名空间 + skipWaiting() + clients.claim()，发布新版本自动换缓存、不残留旧资源。
  4. 离线兜底：fetch 全部 miss 时返回缓存首页（App Shell 模式），保证离线打开不白屏。
方案首选 手写 SW + precache App Shell + 版本指纹；若后续要自动指纹/清理，再评估 Workbox（成熟、维护成本高）。第三方插件（flutter_pwa）依赖维护，不推荐。

1.5 实施要点与风险

要点 / 风险说明
HTTPS 要求SW 仅在 HTTPS 或 localhost 可用；本机验证 OK，生产部署需 HTTPS
canvaskit 多变体构建产物含 6 个 wasm 变体（共 ~25MB），只 precache 实际使用的 chromium 变体，避免浪费
缓存更新必须用版本指纹命名缓存；否则新版本发布后用户仍被旧缓存命中
首屏性能SW 注册放 load 后，避免影响首帧；precache 列表保持精简
调试成本SW 更新有生命周期，开发期建议 DevTools 勾选 bypass，发布前清除旧 SW

2.2 现状的本质：居中手机布局，而非响应式

当前所有端（手机 / 平板 / 桌面）渲染的是同一套手机单列布局，仅通过「居中 + 限宽 560」在宽屏上保持观感。这意味着：

  • 平板 / 桌面信息密度低：560px 两侧大面积空白，大屏优势（多栏、侧边导航、更细的信息层级）完全未利用。
  • 无断点布局系统：没有 compact / medium / expanded 分档，未来要支持桌面双栏需重构。
  • 方向锁定与官方建议冲突：Flutter 官方明确「不要锁定应用的屏幕方向」——桌面 / 平板横屏窗口下 PWA 体验受限，且 Android 大屏分级要求最低级别支持横竖屏。

2.5 建议方向

  1. 引入断点系统：compact（<600）单列 / medium（600–1200）双栏或宽卡片 / expanded（>1200）侧边导航 + 多栏，用 LayoutBuilder 或 MediaQuery 判定。
  2. 平板 / 桌面差异化：大屏采用侧边导航替代底部 dock、题库双栏列表，充分利用宽度。
  3. 移除方向锁定：删除 manifest orientation 或设为 any，支持横竖屏。
  4. 补多尺寸测试：覆盖 390×844（手机竖屏）、768×1024（平板）、1920×1077（桌面）三个典型视口。
